# API

[← README](../README.md)

Полный список с интерактивными схемами — Swagger на http://localhost:8080/docs
(выключен по умолчанию, включается `ENABLE_DOCS=1`).

## Вход

Все маршруты, кроме `/health`, `/ready`, `/metrics` и `/auth/config`, требуют
access-токен Keycloak в заголовке `Authorization: Bearer` либо — для
проверки целей — [ключ доступа](#ключ-доступа-для-внешних-систем). Снаружи
API доступен под `/api` интерфейса; порт 8080 слушает только сам сервер.
Как интерфейс получает токен — в [доступе и безопасности](security.md#как-устроен-вход).

Для проверки руками токен можно взять у Keycloak напрямую, если у realm-а
есть клиент с включённым Direct access grants (у клиента интерфейса он
выключен намеренно):

```bash
TOKEN=$(curl -s https://sso.corp.local/realms/corp/protocol/openid-connect/token \
  -d grant_type=password -d client_id=goal-checker-cli -d username=i.ivanov -d password="…" \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')

curl -s https://<интерфейс>/api/check-goal \
  -H "Authorization: Bearer $TOKEN" -H 'X-Requested-With: XMLHttpRequest' -H 'Content-Type: application/json' \
  -d '{"goal": "Снизить долю просроченных заявок до 5% к 31.12.2025", "department_id": "UCT", "is_student": false}'
```

API принимает токен, у которого наш клиент (`KEYCLOAK_CLIENT_ID`) стоит
в `aud` или `azp`; токен другого клиента, как `goal-checker-cli` выше,
пройдёт, только если у него настроен audience mapper на клиент интерфейса.

### Ключ доступа для внешних систем

Системе, которая проверяет цели без человека (кадровая система), входить
через домен нечем. Ей администратор выдаёт ключ в разделе «Настройки»; ключ
передаётся в заголовке `Authorization` и открывает только `/check-goal`
и `/check-goals` — каталог, настройки и мониторинг по ключу недоступны (`403`).

```bash
curl -s https://<интерфейс>/api/check-goals \
  -H 'Authorization: Bearer gc_1a2b3c4d_…' -H 'Content-Type: application/json' \
  -d '[{"id": "kpi-1", "goal": "…", "department_id": "UCT", "is_student": false}]'
```

Заголовок `X-Requested-With` при запросе с ключом не нужен. Неверный или
отозванный ключ — `401`; проверка по ключам выключена настройкой
`apiKeysEnabled` — `403`. В истории проверок и журнале аудита такая система
видна как `key:<название ключа>`.

### Ограничение частоты

Один пользователь или один ключ проверяет не больше заданного числа целей
в минуту (настройка «Лимит проверок», по умолчанию `CHECK_RATE_PER_MINUTE` = 600; пакет считается по числу целей, ответы из
кэша тоже). Сверх этого — `429` с заголовком `Retry-After` в секундах.
Пакет крупнее самого лимита проходит, если за последнюю минуту запросов не было.

```
GET    /auth/config               {issuer, clientId} — куда интерфейсу идти за входом; без токена
POST   /auth/logout               отметка выхода в журнале; саму сессию закрывает Keycloak
GET    /auth/me                   кто вошёл: {login, role, displayName, tourSeenAt, limits}
POST   /auth/me/tour              обучение пройдено или пропущено → {tourSeenAt}   (не по ключу доступа)

GET    /auth/users                реестр пользователей            (администратор)
POST   /auth/users                {login, role, displayName}      (администратор)
PATCH  /auth/users/{login}        {role, status, displayName}     (администратор)
DELETE /auth/users/{login}                                        (администратор)
DELETE /auth/users/{login}/binding  снять привязку к учётной записи Keycloak (администратор)
```

`tourSeenAt` — когда пройдено обучение по интерфейсу, `null` — ещё нет.
`limits` — пределы запроса проверки, по которым интерфейс режет пакет и текст:
`{maxGoalsPerRequest, goalMaxChars}` (`MAX_GOALS_PER_REQUEST` и настройка `goalMaxChars`, по умолчанию 4000).

В `GET /auth/users` у каждой записи есть `bound` — привязана ли она
к учётной записи Keycloak ([подробнее](security.md#привязка-к-учётной-записи-keycloak)) —
и `builtin` — логин из `AUTH_ADMIN_LOGINS`. У записи без роли (доступ
не назначен) `role` и `status` — `null`.

Изменяющие запросы (`POST`, `PUT`, `PATCH`, `DELETE`) без заголовка
`Authorization` обязаны нести `X-Requested-With: XMLHttpRequest` — без него
ответ `403`. С токеном или ключом доступа этот заголовок не нужен: чужая
страница без CORS не может поставить ни тот, ни другой. Чтение каталога
и проверка целей доступны любой роли, правка — редактору, физическое
удаление, `repair-identifiers`, `merge-duplicate-targets` и `/auth/users` —
администратору; см. [роли](security.md#роли).

## Проверка целей

### Пакетная проверка

```bash
curl -s https://<интерфейс>/api/check-goals \
  -H "Authorization: Bearer $TOKEN" -H 'X-Requested-With: XMLHttpRequest' -H 'Content-Type: application/json' \
  -d '[{"goal": "Снизить долю просроченных заявок до 5% к 31.12.2025", "department_id": "UCT", "is_student": false, "id": "kpi-1"},
       {"goal": "Улучшить работу с заявками", "department_id": "AGD", "is_student": true, "id": "kpi-2"}]'
```

Вход — массив объектов `{"goal": "...", "department_id": "...", "is_student": true, "id": "..."}`.

| Поле | Обязательно | Назначение |
|---|---|---|
| `goal` | да | формулировка цели, не длиннее настройки `goalMaxChars` (по умолчанию 4000 символов); пробелы по краям срезаются; пустая или более длинная цель — `422` |
| `department_id` | да | `departmentId` подразделения, чья это цель, до 100 символов; число принимается как строка; без поля, с пустой строкой или одними пробелами — `422` |
| `is_student` | нет, но передавайте | `true` — цель ставит студент: проверяются и правила только для студентов; `false` — такие правила пропускаются; без поля (или `null`) применяются все правила, причина в `notes`. Разбор нестрогий: кроме `true`/`false` принимаются `1`/`0` и строки `"true"`/`"false"`, `"yes"`/`"no"`, `"on"`/`"off"`, `"1"`/`"0"`; иное значение — `422` |
| `id` | нет | идентификатор вызывающей системы, до 200 символов; возвращается строкой (число `42` — как `"42"`) или `null` |

Ошибка в любом элементе (`422`) отклоняет весь пакет.

Идентификатор, которого нет в графе, пакет не роняет: цель проверяется
по всем правилам, а причина пишется в её `notes` — см.
[разграничение по подразделениям](architecture.md#разграничение-по-подразделениям).
Так же работает и отсутствующий `is_student` —
см. [правила только для студентов](architecture.md#правила-только-для-студентов).

Ответ:

```json
{
  "results": [ { "id": "kpi-1", "goal": "...", "status": "...", "allowed": true,
                 "department": {"id": "UCT", "name": "УЦТ"}, "is_student": false,
                 "detected_attributes": [], "violations": [], "notes": [] } ],
  "summary": { "total": 2, "allowed": 1, "violations": 1, "manual_review": 0 }
}
```

Порядок ответов совпадает с порядком входа. Словари атрибутов и подразделений
читаются один раз на весь пакет, обращения к модели идут параллельно (`BULK_MAX_WORKERS`,
по умолчанию 16, в пределах общей [очереди к модели](architecture.md#нагрузка-очередь-к-модели-и-кэш)) — узкое место именно они. Одинаковые цели пакета (та же
формулировка, подразделение и признак студента) проверяются один раз,
повторы получают тот же ответ. Сбой одной цели — модели, графа или любой
другой — не роняет пакет: она получает `NEEDS_MANUAL_REVIEW`, остальные
проверяются как обычно. Пакет ждёт места в очереди к модели без предела,
а при сработавшем [предохранителе](architecture.md#нагрузка-очередь-к-модели-и-кэш)
ждёт его закрытия до `LLM_BREAKER_BULK_WAIT_SECONDS` (по умолчанию 300 с)
от начала сбоя — потом оставшиеся цели получают `NEEDS_MANUAL_REVIEW`.
Размер пакета ограничен `MAX_GOALS_PER_REQUEST` (по умолчанию 200), при
превышении — `413`. Одновременно на весь сервис идёт не больше
`BULK_MAX_REQUESTS` (по умолчанию 4) запросов `/check-goals`; сверх — сразу
`503` с `Retry-After: 30`, цели не проверяются и в лимит не засчитываются.
Настройка `bulkChecks` выключена — `503` без `Retry-After`;
`smartCheckBulk` выключена — пакет идёт без оценки по SMART (`smart: null`).

Пакет отвечает не позже `BULK_DEADLINE_SECONDS` (по умолчанию
600 − `LLM_TIMEOUT_SECONDS` − `LLM_CONNECT_TIMEOUT_SECONDS` − 15, то есть
520 с: после остановки запрос к модели, уже бывший в полёте, дожидается
ответа или таймаута, а новые запросы и повторы не уходят — так ответ
укладывается в таймаут прокси интерфейса в 600 с; срок, с которым это не
так, API при старте отмечает предупреждением в журнале) и останавливается,
если клиент закрыл соединение: цели, до которых не дошли, и цели, ждущие
очереди к модели или закрытия предохранителя, приходят `NEEDS_MANUAL_REVIEW`
с заметкой «Цель не проверена: пакет не уложился в отведённое время или
запрос был прерван. Отправьте её на проверку повторно.» и полем
`"unchecked": true` — по нему клиент отличает непроверенную цель от
настоящей ручной проверки (у проверенных целей поля нет). Такой ответ не
кэшируется и не пишется в историю и в показатели ручных проверок; одинаковая
цель из другого, не остановленного пакета проверяется сама, а не получает
этот ответ. Лимит проверок списывается за весь пакет при приёме, а за
непроверенные цели возвращается после ответа — их можно сразу отправить снова.

### Прочее

```bash
curl -s localhost:8080/health          # liveness, без входа
curl -s localhost:8080/ready           # readiness: Neo4j, диагностика графа и vLLM; без входа, только с сервера
```

`GET /check-targets` — словарь проверяемых атрибутов, `POST /check-goal` —
одна цель (пример — в разделе «Вход»).

В одиночной проверке `department_id` и `is_student` необязательны: без них
применяются все правила, а в `notes` появляется причина. Цель — не длиннее `goalMaxChars` (по умолчанию 4000)
символов, пустая — `422`. `department_id` — до 100 символов (длиннее — `422`),
число принимается как строка, пробелы по краям срезаются; пустая строка
или одни пробелы — то же, что без поля.

Ручная проверка (`/check-goal`) ждёт места
в [очереди к модели](architecture.md#нагрузка-очередь-к-модели-и-кэш) не
дольше `LLM_QUEUE_TIMEOUT_SECONDS` (по умолчанию 120 с, `0` — без предела);
не дождалась — `503` с `Retry-After: 30`, а не ответ «требуется ручная
проверка». Ручная проверка не ждёт идущую пакетную проверку той же цели
и идёт к модели сама; одинаковые ручные проверки, идущие одновременно,
ждут одну. Ручных проверок в работе и в ожидании на весь сервис не больше
`CHECK_MAX_PENDING` (по умолчанию вдвое больше `llmMaxConcurrency`); сверх —
сразу `503` с `Retry-After: 10`, цель не проверяется и в лимит не
засчитывается. Проверка по ключу внешней системы ждёт с тем же пределом, но
резерв `llmInteractiveReserve` ей не положен — он остаётся людям в
интерфейсе, — и её допускается на `2 × llmInteractiveReserve` меньше.

`/health` ни к чему не обращается и отвечает, пока жив процесс.
`/ready` опрашивает одновременно Neo4j и модель: `GET /v1/models` с ключом
`VLLM_API_KEY` (до 2 с) и есть ли в списке `VLLM_MODEL` — так видны неверный
ключ и имя модели, а не только живой процесс. Удачный ответ модели помнится
45 с, неудачный — нет. Всё вместе — не дольше 15 с. В ответе `neo4j`, `llm`
(готова ли модель), `check_targets`, `problems` (для модели — причина: нет
ответа, ключ отклонён, модели нет в списке), полный отчёт `diagnostics` и
`clock_skew_seconds` — расхождение часов API и Keycloak, замеченное по
токенам за последний час (больше 0 — часы API отстают; `null` — не замечено;
[подробнее](security.md#как-устроен-вход)). Ответ `503`, если
Neo4j недоступен, модель не готова или в графе есть ошибки диагностики:
пустой словарь атрибутов, двойники атрибутов, атрибуты без описания, правила
без атрибутов, узлы без идентификатора, текстовые свойства с нестроковым
значением, на которых держится проверка (`non_text_properties`: имя и
описание атрибута, `departmentId` подразделения) — то есть когда проверка
целей не работает или молча неполна. Предупреждения (например, атрибуты без
правил, слишком длинные тексты `too_long_texts`, нестроковые номер, название
или описание, которые только показываются, `non_text_display_properties`)
готовности не мешают.
Разбор каждой проверки — в [диагностике](web-ui.md#диагностика).

`GET /metrics` — показатели в текстовом формате Prometheus, без входа и, как
`/ready`, только с самого сервера (`localhost:8080/metrics`; через интерфейс —
`404`). Считается в тех же отдельных потоках, что `/ready`. Все имена
начинаются с `goal_checker_`:

| Показатель | Что значит |
|---|---|
| `llm_capacity`, `llm_running`, `llm_waiting` | предел запросов к модели, запросов в работе и ждущих очереди |
| `checks_running`, `bulk_batches`, `bulk_queued_goals` | проверок в работе, пакетов в работе, целей пакетов, до которых не дошла очередь |
| `single_checks_admitted`, `single_checks_rejected_total` | ручных проверок в работе и в ожидании; отклонённых `503` сверх `CHECK_MAX_PENDING` (счётчик) |
| `recent_checks`, `recent_manual_review`, `recent_manual_review_ratio` | проверок и ответов `NEEDS_MANUAL_REVIEW` за последние 5 минут, их доля |
| `llm_breaker_open{kind="single"\|"bulk"}` | разомкнут ли предохранитель модели (1/0) |
| `history_pending`, `history_dropped_total` | записей истории, ждущих записи в Neo4j; потерянных при переполнении (счётчик) |
| `clock_skew_seconds` | расхождение часов API и Keycloak; только если замечено за последний час |
| `uptime_seconds` | сколько работает процесс API |

Ответ `/check-goal`:

```json
{
  "goal": "...",
  "status": "ALLOWED | VIOLATIONS_FOUND | NEEDS_MANUAL_REVIEW",
  "allowed": false,
  "department": {"id": "UCT", "name": "УЦТ"},
  "is_student": false,
  "detected_attributes": ["срок_исполнения", "измеримость"],
  "attribute_quotes": {"срок_исполнения": "до 31 декабря 2026 года", "измеримость": "на 15%"},
  "smart": {
    "specific": {"score": 80, "comment": "Названы предмет и результат."},
    "measurable": {"score": 90, "comment": "Есть показатель — 15%."},
    "achievable": {"score": 70, "comment": "Объём посилен за год."},
    "relevant": {"score": 40, "comment": "Не видно, зачем цель нужна."},
    "time_bound": {"score": 95, "comment": "Срок назван."}
  },
  "violations": [
    {
      "order_number": "ПР-01",
      "order_title": "О порядке постановки целей",
      "clause_code": "1.1",
      "clause_text": "...",
      "rule_id": "R-1.1",
      "rule_node_id": "4:…:12",
      "rule_text": "...",
      "check_instruction": "Проверь, указан ли в тексте цели проект...",
      "violation_type": "MISSING_REQUIREMENT",
      "attribute": "проект",
      "example_kind": "correct",
      "examples": ["..."],
      "matched_duties": [{"job_description_id": "UCT/аналитик", "title": "Аналитик", "duty": "..."}]
    }
  ],
  "unverified_rule_node_ids": [],
  "notes": []
}
```

`department` — найденное подразделение или `null`, если оно не передано,
неизвестно графу или в архиве: тогда применены все правила, причина в `notes`.
`is_student` — признак из запроса как есть; `null` — не передан, и правила
только для студентов тоже применены.

`smart` — оценка по [SMART](architecture.md#оценка-по-smart): пять критериев
(`specific`, `measurable`, `achievable`, `relevant`, `time_bound`), у каждого
`score` от 0 до 100 и `comment` одним предложением. Это справка автору цели,
на `status` она не влияет. `null` — настройка `smartCheck` выключена,
в пакете выключена `smartCheckBulk` или модель не ответила (тогда причина
в `notes`). Ответ из кэша ручной проверке, если оценки этой формулировки
нет в памяти API, ждёт её не дольше 1 с, а свежая ручная проверка после
готового вердикта — не дольше 10 с (оценку той же формулировки может
считать пакет или фоновая задача): не успела — `smart: null`
и заметка «Оценка по SMART ещё считается и появится при следующей проверке
этой цели», а оценка досчитывается в фоне.

Оценка зависит только от текста цели: одинаковая формулировка (с точностью
до пробелов по краям и между словами) получает одинаковую оценку независимо
от `department_id`, `is_student`, правок каталога и срока кэша ответов.
У модели она спрашивается один раз, затем хранится в памяти API
(`SMART_CACHE_TTL_SECONDS`, по умолчанию сутки) и в графе (`:SmartScore`,
`SMART_SCORE_RETENTION_DAYS`, по умолчанию 365 дней), то есть переживает
перезапуск. В кэше готовых ответов оценка не хранится — подставляется при
выдаче. Сбой модели не запоминается: следующая проверка той же цели спросит
её снова. Выключение и включение `smartCheck` очищает оценки в памяти, но
не в графе.

Ключ кэша готовых ответов — SHA-256 цели со схлопнутыми пробелами,
подразделение и признак студента: цели, отличающиеся только пробелами,
делят одну запись. `goal` в ответе — как передано в запросе, но с
пробелами по краям, срезанными при разборе.

`rule_node_id` — `nodeId` правила (`elementId`), по нему правило открывается
в каталоге (`/catalog/nodes/{nodeId}`).

`matched_duties` есть только у нарушений по атрибуту, который определяется
сравнением с [должностными инструкциями](architecture.md#должностные-инструкции):
обязанности, с которыми совпала цель; каждая дословно (с точностью до
регистра и пробелов) есть в тексте названной инструкции. Если сравнить цель
с инструкциями не удалось, а других нарушений нет, статус —
`NEEDS_MANUAL_REVIEW`; требование на таком атрибуте при сбое сравнения
нарушением не считается, а уходит на ручную проверку. Такой ответ не
кэшируется. Длинная инструкция не обрезается: она сравнивается по частям
с перекрытием на стыках, и обязанность из любой части засчитывается.

`unverified_rule_node_ids` — `nodeId` правил, которые проверить не удалось
(правила на атрибутах «по инструкции», когда сравнение с инструкциями не
состоялось): они не нарушены и не выполнены, интерфейс не ставит им ✓.
У ответа ручной проверки из-за сбоя модели список пуст — там не проверено
ничего, это видно по статусу.

`unchecked` — есть только у цели пакета, которую не проверили (пакет
остановлен по сроку или обрыву соединения), и равно `true`; статус у неё —
`NEEDS_MANUAL_REVIEW`, но цель надо отправить снова (см. выше про
`BULK_DEADLINE_SECONDS`).

`retryable` — есть только у ответа ручной проверки из-за временного сбоя
(модель, база; заметка «Проверку не удалось завершить из-за временного сбоя
сервиса…») и равно `true`: цель не разбирали, её можно отправить снова.
Интерфейс повторяет такие цели кнопкой «Проверить оставшиеся».

`notes` — не декоративное поле. Туда попадают атрибуты, которых нет
в словаре графа, обнаруженные двойники написаний, неопределённое
подразделение и непереданный признак студента: это причины, по которым
результат проверки может быть неполным или строже ожидаемого.

Сбой модели описывается в `notes` общей причиной, без подробностей
из лога: «модель недоступна», «модель не ответила вовремя», «модель
не отвечает, проверка повторится позже» (сработал предохранитель после
`LLM_BREAKER_TIMEOUTS` таймаутов подряд; у пакета — после
`LLM_BREAKER_BULK_WAIT_SECONDS` ожидания), «цель вместе с инструкциями
не помещается в окно модели», «модель отклонила запрос», «ответ модели
не по форме», «модель отклонила ключ или имя модели — проверьте VLLM_URL,
VLLM_MODEL и VLLM_API_KEY» (ответ модели 401, 403 или 404 — ошибка
настройки, без повторов), «модель перегружена: превышен лимит запросов»
(ответ 429 после `LLM_MAX_RETRIES` повторов с паузой до 5 с). Непредвиденный сбой (граф, ошибка в коде) даёт
`NEEDS_MANUAL_REVIEW` с заметкой «Проверку не удалось завершить из-за
временного сбоя сервиса. Требуется ручная проверка.» — подробности только
в логе API.

Оба типа нарушений возвращаются с одинаковым набором полей; различать их
следует по `violation_type` и `example_kind` (`violation` — так делать нельзя,
`correct` — образец правильной формулировки).

### Режим отказа: fail-closed

Если извлечь атрибуты не удалось (модель недоступна, вернула не JSON,
словарь `CheckTarget` пуст), ответ будет `status: NEEDS_MANUAL_REVIEW`
и `allowed: false`, а причина — в `notes`. Проверка соответствия
никогда не «разрешает» цель из-за собственного сбоя.

## Мониторинг

Только администратору.

```
GET /monitoring/now                              очередь к модели, пакеты в работе, показатели за 5 минут, vLLM, кэш
GET /monitoring/stats?start=&end=&step=&timezone=&mode=&status=
                                                 средние показатели за период; step: minute | hour | day | week | month
GET /monitoring/history?start=&end=&limit=&offset=&mode=&status=
                                                 проверки за период постранично: {records, total}; limit до 100, по умолчанию 10
```

`start` и `end` — ISO 8601, конец не включается. `timezone` — имя IANA
(например `Europe/Moscow`) или смещение `±HH:MM`, по умолчанию `UTC`; задаёт
границы интервалов. Неверные `start`, `end`, `timezone`, `step`, `status`,
`mode` или период больше 2000 интервалов — `422`, недоступная база — `503`.
В каждом интервале и в `totals`: `total`, `avg_ms`, `avg_computed_ms`,
`p95_ms`, `max_ms`, `avg_queue_ms`, `avg_llm_ms`, `llm_calls`, `cached`,
`allowed`, `violations`, `manual_review`. `avg_computed_ms`, `p95_ms`,
`avg_queue_ms` и `avg_llm_ms` считаются без ответов из кэша.

В `/monitoring/now` `checks.batches` — пакеты в работе (`total`, `done`,
`running` — цели пакета, которые проверяются сейчас), `checks.queued` —
цели принятых пакетов, до которых очередь ещё не дошла; ручные проверки
туда не входят. Среднее время в `recent` — тоже без ответов из кэша.

## Настройки и ключи доступа

Только администратору.

```
GET    /settings                                 все настройки: {promptExamples, injectionGuard, …}
PUT    /settings                                 меняет переданные настройки; число вне границ — 422
GET    /settings/api-keys                        ключи: {keys: [{keyId, name, createdAt, createdBy, lastUsedAt}]}
POST   /settings/api-keys                        {name} → тот же объект и key — сам ключ, показывается один раз
DELETE /settings/api-keys/{keyId}                отозвать ключ; действует со следующего запроса
GET    /settings/caches                          кэши проверки: {caches: [{id, entries, max_entries, ttl_seconds, hits, misses}]}
POST   /settings/caches/{id}/clear               очистить один кэш; {departmentId} — только записи подразделения
```

Кэши (`id`): `results` — готовые ответы проверок, `jobDescriptions` — должностные
инструкции подразделений и правила на них, `smart` — оценки по SMART,
`lookups` — справочники каталога (настройки, примеры для промпта). По подразделению
делятся только `results` и `jobDescriptions`; для остальных `departmentId` — 422.
Очистка `smart` удаляет и оценки, сохранённые в графе, — следующая проверка
каждой формулировки спросит модель заново; если граф недоступен, память очищается,
а ответ — 503. Ответ: `{cache, entries, stored, departmentId}`, где `entries` —
сколько записей убрано из памяти, `stored` — сколько оценок удалено из графа
(только для `smart`).

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `promptExamples` | `false` | к атрибутам в промпте добавляются примеры из каталога — см. [архитектуру](architecture.md#примеры-в-промпте) |
| `injectionGuard` | `true` | цель с текстом, похожим на указания модели, получает `NEEDS_MANUAL_REVIEW` вместо `ALLOWED` — см. [безопасность](security.md#указания-модели-в-тексте-цели) |
| `evidenceQuotes` | `true` | модель подтверждает каждый найденный атрибут цитатой из цели (`attribute_quotes`); если цитаты в тексте цели нет, цель получает `NEEDS_MANUAL_REVIEW` вместо `ALLOWED` |
| `smartCheck` | `true` | оценка цели по SMART отдельным запросом к модели (поле `smart`); на `status` не влияет; смена значения очищает кэш оценок в памяти |
| `smartCheckBulk` | `true` | `false` — пакетная проверка (`/check-goals`) идёт без оценки по SMART, `smart: null`; действует, только пока включена `smartCheck` |
| `promptExamplesPerKind` | `2` | сколько примеров «есть» и «нет» на атрибут уходит в промпт; от 1 до 10 |
| `checkCache` | `true` | помнить ответ на ту же цель того же подразделения с тем же признаком студента |
| `checkCacheTtlSeconds` | `3600` | срок жизни ответа в кэше, с; от 0 до 604800 |
| `jobDescriptionsCacheTtlSeconds` | `60` | сколько секунд проверка помнит [должностные инструкции](architecture.md#должностные-инструкции) подразделения и правила на них; правка каталога сбрасывает кэш сразу; `0` — читать из графа на каждую проверку; до 86400 |
| `bulkChecks` | `true` | `false` — `/check-goals` отвечает `503`, `/check-goal` работает |
| `checkRatePerMinute` | `600` | целей в минуту на пользователя или ключ; `0` — без ограничения; до 100000 |
| `goalMaxChars` | `4000` | предел длины цели в символах для `/check-goal`, `/check-goals` и советчика; от 100 до 8000; длиннее — `422` (`string_too_long`, в `ctx.max_length` — текущий предел); интерфейс берёт его из `/auth/me` и проверяет до отправки. Выше 4000 цель вместе с должностными инструкциями может не поместиться в окно модели, и проверка уйдёт на ручную |
| `historyEnabled` | `true` | проверки записываются в историю |
| `historyRetentionDays` | `365` | срок хранения истории, дней; `0` — не удалять; до 3650 |
| `apiKeysEnabled` | `true` | `false` — любой запрос с ключом доступа получает `403`, ключи при этом не отзываются |
| `maintenance` | `false` | режим обслуживания: всем, кроме администратора, проверка и каталог отвечают `503` с `Retry-After`; ключам доступа тоже; вход и `/auth/me` работают |
| `llmMaxConcurrency` | `32` | одновременных запросов к модели на весь сервис, остальные ждут в очереди API; от 1 до 256; действует сразу, работающие запросы не прерываются — см. [архитектуру](architecture.md#нагрузка-очередь-к-модели-и-кэш) |
| `llmInteractiveReserve` | `4` | слотов из предела, недоступных пакетной проверке; от 0 до 255; в ответе обрезан до `llmMaxConcurrency - 1` |

У числовых настроек значение по умолчанию берётся из одноимённой переменной
окружения (`PROMPT_EXAMPLES_PER_KIND`, `CHECK_CACHE_TTL_SECONDS`,
`JOB_DESCRIPTIONS_CACHE_TTL_SECONDS`, `CHECK_RATE_PER_MINUTE`, `GOAL_MAX_CHARS`,
`HISTORY_RETENTION_DAYS`, `LLM_MAX_CONCURRENCY`, `LLM_INTERACTIVE_RESERVE`)
и действует, пока настройку не сохранили через API. Готовые ответы проверок сбрасываются только при смене
настроек, от которых зависит ответ модели: `promptExamples`, `promptExamplesPerKind`,
`injectionGuard`, `evidenceQuotes`, `smartCheck`, `smartCheckBulk`.

Настройки читаются из графа; если граф не отвечает, служат последние
прочитанные. Пока их не удалось прочитать ни разу (API только запустился,
а Neo4j недоступен), `maintenance` и `apiKeysEnabled` считаются запрещающими:
пользователям, кроме администратора, и ключам доступа — `503` «Настройки
сервиса не прочитаны: граф недоступен. Попробуйте позже».


Тело `PUT /catalog/rules/{nodeId}/departments` заменяет область действия целиком:

```json
{"only": ["UCT", "AGD"]}
```

Пустой список — правило действует для всех.

Защита от одновременных правок. `PUT /catalog/rules/{nodeId}/targets`,
`PUT …/departments` и `PUT /catalog/clauses/{nodeId}/references` принимают
необязательное поле `expected` — прежний набор, который видел редактор, в том
же формате, что основной список:

```json
{"only": ["UCT", "AGD"], "expected": ["UCT"]}
```

Если в базе набор уже другой (сравнивается как множество), ответ `409`
«Узел изменён другим пользователем — обновите страницу и повторите правку»,
ничего не записано. Без `expected` набор заменяется, как раньше.

Изменяющие запросы каталога сбрасывают кэш готовых ответов и увеличивают
[версию каталога](architecture.md#версия-каталога-и-кэш-ответов), только если
дошли до самой операции и она удалась или упала непредвиденно (`500` — могла
записать часть). Отклонённые — `403`, `422`, `404`, `409` — кэш и версию
не трогают.

`repair-identifiers` одной транзакцией проставляет недостающие `orderId`,
`clauseId`, `ruleId`, `exampleId`, `jobDescriptionId`
(`<departmentId>/<slug названия>`) и `status: active`; в ответе — сколько
узлов каждого вида исправлено. Имя атрибута и `departmentId` — смысловые
ключи, они не придумываются: `unnamedTargets` и `departmentsWithoutId` —
`nodeId` таких узлов, им ключ задают вручную.

`merge-duplicate-targets` сводит только двойников с одинаковыми `status`
и `source`: перенос правил с архивного атрибута на действующий включил бы
отключённые правила, а атрибут «по инструкции» проверяется иначе.
Остаётся узел с описанием, затем с большим числом правил. Группы, где
статус или `source` различаются, попадают в `skipped` с причиной — их
сводят вручную (архивировать лишний или выровнять `source`).

`POST /catalog/rules` принимает необязательные `studentsOnly` (по умолчанию
`false`) и `only` — область действия, как в `/departments` (по умолчанию
пустая, то есть для всех). Атрибуты и подразделения проверяются до создания,
правило со связями создаётся одной транзакцией: неизвестный атрибут или
подразделение — `404`, и правило не появляется. Позже признак меняется через
`/audience` или правкой свойства `studentsOnly` в `PATCH …/properties`.

Замена связей (атрибуты, область действия, ссылки) и перенос идут одной
транзакцией с блокировкой узла. Перенести пункт или правило в архивный
приказ или пункт, а правило — и в действующий пункт архивного приказа,
нельзя — `409`. Непереданные `clauseId`
и `jobDescriptionId` строятся автоматически с первым свободным суффиксом
(`.2`, `.3`…), `ruleId` получает свободный суффикс и тогда, когда передан;
занятый переданный ключ приказа, пункта, подразделения или инструкции —
`409`, в том числе когда его одновременно занял параллельный запрос.

### Правка свойств

`PATCH /catalog/nodes/{nodeId}/properties` с `{"properties": {…}}` пишет
переданные свойства, `null` удаляет свойство с любым именем — и старое
с «неудобным» именем тоже, кроме перечисленных ниже служебных
и защищённых.

Необязательное `expected` — значения, которые видел редактор, в том виде,
в каком их отдал `GET /catalog/nodes/{nodeId}` (отсутствующее свойство —
`null`): `{"properties": {"description": "новое"}, "expected": {"description": "прежнее"}}`.
Если в базе любое из них уже другое — `409` «Узел изменён другим
пользователем…» с именами изменившихся свойств, ничего не записано. Сверка
и запись идут в одной транзакции под блокировкой узла.

Так же работает `expected` у должностной инструкции:

- `PUT /catalog/job-descriptions/{nodeId}` с
  `{"title": "…", "text": "…", "expected": {"title": "прежняя", "text": "прежний"}}`
  — если в базе должность или текст уже другие, `409` с тем же текстом
  («Узел изменён другим пользователем… Изменились: text»): форма из старого
  снимка не откатит чужой текст и не перезапустит его выписку обязанностей;
- `PUT /catalog/job-descriptions/{nodeId}/duties` с
  `{"duties": [...], "expected": [...]}` — прежний список сравнивается
  с базой как упорядоченный (порядок и повторы важны; инструкция без списка
  равна `[]`), расхождение — `409`.

Сверка и запись — одной транзакцией под блокировкой узла. Без `expected`
оба запроса пишут, как раньше.

Строковые значения известных текстовых свойств (см. пределы ниже) и
бизнес-ключа узла сохраняются без пробелов по краям — так же, как при
создании: `departmentId` `" 5 "` записывается как `"5"`. Пустая после
этого строка — как пустая.

Отклоняется с `422`:

- текстовое свойство не строкой (число, `true`/`false`, список) или длиннее
  предела — тех же, что при создании (`catalog.TEXT_LIMITS`): номер приказа
  100, название приказа 500, номер пункта 50, текст пункта 8000, описание
  и инструкция правила 4000, текст примера 4000, имя атрибута 200, описание
  атрибута 4000, `departmentId` 100, название подразделения 500, должность
  в инструкции 500; прочие строки (и каждая строка списка) — до 8000;
- пустое или удаляемое (`null`) обязательное текстовое свойство (кроме
  `checkInstruction` правила и `description` атрибута);
- служебные метки шаблона модели в тексте (`<|…|>`, `<think>`,
  `<tool_call>`, `<tool_response>`) — тексты каталога уходят в системное
  сообщение модели, и метка закрыла бы его раньше времени
  ([подробнее](security.md#указания-модели-в-тексте-цели)). Так же `422`
  получают такие метки и при создании узлов (`POST /catalog/…`,
  `PUT /catalog/job-descriptions/…`, список обязанностей).

Отклоняется с `409`:

- новое имя не из букв, цифр и `_`, начинается не с буквы (с цифры или `_`)
  или длиннее 64 символов; имена `nodeId`, `labels` и `_lock` заняты
  служебными полями;
- значение не скаляр (строка, число, `true`/`false`) и не однородный список
  скаляров; `NaN`, бесконечность и целые вне 64 бит;
- `status` (меняется через `/status`), у инструкции — `text`, `duties`,
  `dutiesReviewed`, `dutiesStatus`, `dutiesError`;
- неверные значения управляющих свойств: `Rule.type` (`PROHIBITION` /
  `REQUIREMENT`), `Rule.studentsOnly` и `ViolationExample.isViolation`
  (только `true`/`false`), `CheckTarget.source` (`job_descriptions` или пусто),
  `Order.date` (`ГГГГ-ММ-ДД`);
- пустой, не строковый или занятый другим узлом бизнес-ключ, двойник
  атрибута по написанию.

### Должностные инструкции и обязанности

Выписка обязанностей — несколько запросов к модели подряд, дольше таймаутов
прокси, поэтому она идёт в фоне. `POST /catalog/job-descriptions`,
`PUT …/{nodeId}` с новым текстом и `POST …/extract-duties` отвечают `202`
с узлом в состоянии `dutiesStatus: "pending"`; интерфейс опрашивает
`GET /catalog/job-descriptions/{nodeId}`, пока статус не станет `ready`
или `error`:

| `dutiesStatus` | Что значит |
|---|---|
| `pending` | обязанности выписываются |
| `ready` | список `duties` готов (у инструкций, загруженных до фоновой выписки, — всегда) |
| `error` | модель не ответила; причина в `dutiesError`, проверка идёт по полному тексту инструкции |

Одновременно выписывается не больше `DUTIES_WORKERS` инструкций (1 или 2),
остальные ждут. Если обязанностей больше 300, сохраняются первые 300,
а предупреждение — в `dutiesError` при статусе `ready`. Выписка, оборванная
остановкой или перезапуском API, при следующем старте помечается `error`
(«Выписка прервана перезапуском»): остановка API идущую выписку не ждёт,
очередь невыписанных отменяется. Итог выписки при сбое Neo4j записывается
до 3 раз; если так и не записался, «зависший» `pending` при следующем
`GET` инструкции переводится в `error` с причиной «Выписка прервана: итог
не сохранился (сбой базы), запустите заново». `extract-duties` при таком
`pending` перезапускает выписку (`202`); `409` — только если выписка
действительно идёт.

### Советчик по графу

`POST /catalog/advice` — редактор не согласен с ответом проверки по одному
атрибуту одной цели:

```json
{
  "goal": "Сдать отчёт во втором квартале",
  "attribute": "срок_исполнения",
  "expected": true,
  "reason": "квартал — проверяемый срок",
  "department_id": "UCT"
}
```

`expected` — каким ответ должен быть: `true` — атрибут найден. `department_id`
нужен только атрибуту, определяемому по должностным инструкциям; до 100
символов, пустая строка — то же, что без поля. Ответ:

```json
{
  "attribute": "срок_исполнения", "nodeId": "4:…:7", "source": null, "expected": true,
  "current": {"present": false, "evidence": null},
  "already": false,
  "diagnosis": "в описании перечислены только даты…",
  "description": {"old": "…", "new": "…", "verified": true, "attempts": 1},
  "regression": {"checked": 6, "broken": [], "alreadyWrong": 1, "failed": 0},
  "examples": [{"ruleNodeId": "4:…:12", "ruleId": "R-2.4", "ruleType": "REQUIREMENT",
                "ruleText": "…", "isViolation": false}],
  "examplesInPrompt": false,
  "notes": []
}
```

| Поле | Что означает |
|---|---|
| `current` | что модель отвечает сейчас (мимо кэша); `evidence` — цитата цели или обязанность из инструкции |
| `already` | модель уже отвечает как нужно — предложений нет |
| `description` | новое описание атрибута; `verified` — с ним модель ответила на цель как нужно, `attempts` — сколько описаний перебрано |
| `regression` | примеры каталога с новым описанием: `broken` — перестали распознаваться верно, `alreadyWrong` — модель ошибалась и раньше; `null` — не проверялись |
| `examples` | правила, которым цель можно добавить примером, и с какой пометкой |

Предложение применяется обычными запросами: `PATCH /catalog/nodes/{nodeId}/properties`
с `{"properties": {"description": "…"}}` и `POST /catalog/examples`. `404` —
атрибута нет, `409` — атрибуту по должностным инструкциям не хватает подразделения
или инструкций, `503` — модель не ответила, очередь к ней не подошла
(тогда с `Retry-After: 30`) или совет остановлен.

Совет идёт не дольше 300 с — раньше, чем прокси интерфейса перестанет ждать
ответа, — и останавливается, если клиент закрыл соединение: запросы к модели,
ждущие очереди, снимаются, ответ — `503` «Модель не ответила: совет
остановлен: не уложился в срок или запрос был прерван». Отдельно очередь
к модели ждёт не дольше `LLM_QUEUE_TIMEOUT_SECONDS` только подбор описания;
проверка нового описания на примерах каталога идёт как пакет — мимо резерва
ручных проверок и без своего предела ожидания, в пределах общего срока.
Обязанность, которой нет в тексте инструкции, атрибут «по инструкции»
не подтверждает — как и при проверке.

## Коды ответов

| Код | Когда |
|---|---|
| `401` | нет токена, он истёк или не прошёл проверку (подпись, издатель, срок, тип); неверный или отозванный ключ доступа |
| `403` | не хватает роли; доступ не назначен; изменяющий запрос без `Authorization` и без `X-Requested-With`; проверка по ключам выключена; токен подлинный, но пустить по нему нельзя — см. ниже |
| `404` | узла нет |
| `409` | операция противоречит состоянию графа: двойник по написанию, удаление неархивированного узла, используемый атрибут или подразделение, занятый бизнес-ключ, перенос в архив, недопустимое свойство, выписка обязанностей действительно идёт; узел изменён другим пользователем (не совпало `expected`) |
| `413` | пакет больше `MAX_GOALS_PER_REQUEST` |
| `422` | не прошла валидация схемы или параметров; текстовое свойство каталога не строкой, длиннее предела или со служебными метками шаблона модели |
| `429` | слишком много проверок за минуту, с `Retry-After` |
| `503` | зависимость недоступна (Neo4j, Keycloak, модель); очередь к модели не подошла — с `Retry-After: 30`; ручных проверок больше `CHECK_MAX_PENDING` — с `Retry-After: 10`; уже идут `BULK_MAX_REQUESTS` пакетов — с `Retry-After: 30`; советчик не уложился в 300 с или клиент ушёл; режим обслуживания для всех, кроме администратора; настройки ни разу не прочитаны; пакетная проверка выключена |

Подлинный токен, по которому пустить нельзя, получает `403`, а не `401`:
повторный вход выдал бы такой же токен. `detail` — текст для пользователя:

- «Токен выдан другому приложению. Войдите в Goal Checker заново» — у токена
  в `aud`/`azp` нет `KEYCLOAK_CLIENT_ID`;
- «Логин учётной записи не подходит для Goal Checker: допустимы латинские
  буквы, цифры, точка, дефис и подчёркивание. Обратитесь к администратору»;
- «Доступ к интерфейсу не назначен. Обратитесь к администратору» — логина
  нет в реестре, он без роли или заблокирован;
- «Логин закреплён в реестре за другой учётной записью Keycloak. Обратитесь
  к администратору» — см. [привязку](security.md#привязка-к-учётной-записи-keycloak).
