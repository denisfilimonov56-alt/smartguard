# Ход проверки цели и пакета

[← README](../README.md)

Контракт API для блока «Ход проверки» в интерфейсе (`web/src/features/check/CheckProgress.tsx`,
`BatchProgress.tsx`). Реализация — `api/main.py` (эндпоинты и хранение), `api/agent.py`
(`CheckTrace`, `BatchTrace`); эталон поведения в mock — `web/mock/backend.ts` (`liveModel`).

Пока идёт проверка, интерфейс показывает, что делает сервис: шаги, их время,
токены модели и найденные атрибуты. Для этого он шлёт в `POST /check-goal`
и `POST /check-goals` заголовок `X-Check-Id` (свой номер, 8–64 символа
`A-Z a-z 0-9 _ -`, обычно UUID) и раз в 0,4–0,5 с спрашивает:

- `GET /check-progress/{id}` — ход одной цели, тип `CheckProgress` в `web/src/api/client.ts`;
- `GET /batch-progress/{id}` — ход одного пакетного запроса (одной части пакета), тип `BatchProgress`.

Ответы самих `/check-goal` и `/check-goals` от заголовка не меняются, а
внешней системе с ключом ход не пишется вовсе: с ключом заголовок
игнорируется, запрос к модели идёт как раньше, без потока. Ход отдаётся только
вошедшему пользователю (`viewer` и выше; ключ — `403`) и только тот, что он
сам запустил: чужой номер, неизвестный, кривой (тогда ход не заводится) или
уже занятый другим запросом — `404` («Проверка не найдена» / «Пакет не
найден»). Ход одной цели и ход пакета — разные пространства номеров.

```json
{"elapsedSeconds": 3.4,
 "stages": [
   {"key": "cache", "status": "done", "seconds": 0.0, "detail": "нет — проверяем заново", "tokens": null},
   {"key": "queue", "status": "done", "seconds": 0.0, "detail": "место получено", "tokens": null},
   {"key": "attributes", "status": "running", "seconds": null, "detail": "модель ищет атрибутов: 12", "tokens": 41},
   {"key": "jobs", "status": "running", "seconds": null, "detail": "сравниваем с инструкциями: 3", "tokens": 18},
   {"key": "smart", "status": "done", "seconds": 1.9, "detail": "готово", "tokens": 96},
   {"key": "rules", "status": "waiting", "seconds": null, "detail": "", "tokens": null}],
 "tokens": {"prompt": 1240, "completion": 155},
 "tokensPerSecond": 48,
 "attributes": [{"name": "проект", "quote": "проекту Альфа"}],
 "matchedDuties": ["Готовит ежемесячный отчёт"]}
```

Шаги — всегда шесть, в этом порядке; `status`: `waiting`, `running`, `done`,
`skipped`; `seconds` — только у `done`; `tokens` — у шагов, обращавшихся к модели.

| Шаг | Что это | `detail` |
|---|---|---|
| `cache` | готовый ответ в кэше или такая же проверка, идущая сейчас | `ответ из кэша` (остальные шаги — `skipped` с той же причиной), `нет — проверяем заново` |
| `queue` | очередь к модели: `running`, пока хоть один запрос проверки ждёт места | `место получено`, `место не получено` (503 очереди, остановка пакета) |
| `attributes` | атрибуты в тексте цели; найденные появляются в `attributes`, как только модель их дописала | `найдено N из M`, `не удалось: …` |
| `jobs` | сравнение с должностными инструкциями подразделения | `есть совпадение с обязанностью`, `совпадений нет`, `не удалось сравнить…`; `skipped` — почему: нет правил, подразделения, инструкций |
| `smart` | оценка SMART | `готово`, `из кэша оценок`, `не получена: …`; `skipped` — выключена в настройках |
| `rules` | поиск сработавших правил в графе | `нарушений: N` |

`attributes`, `jobs` и `smart` у одной цели идут одновременно, в пакете — по
очереди в потоке цели. Когда проверка закончилась, ход застывает: шаг, который
ещё шёл, — `skipped` «не дождались — ответ без этого шага» (например, SMART
досчитывается в фоне), так и не начатый — `skipped` «не понадобилось»;
`attributes` и `matchedDuties` — из ответа проверки.

Токены: пока модель пишет, каждый кусок потокового ответа считается за токен;
по окончании ответа vLLM присылает `usage` (`stream_options.include_usage`) —
тогда `completion` уточняется, а `prompt` прибавляется (до этого запрос в
токенах не виден). `tokensPerSecond` — токенов ответа в секунду от первого
полученного места в очереди до последнего куска; `null`, пока прошло меньше 0,2 с.
Потоком читаются только проверки с ходом: им, как и ответу без потока,
отводится `LLM_TIMEOUT_SECONDS` на весь ответ.

`BatchProgress`: `elapsedSeconds`, `total`, `done`, `tokens`,
`tokensPerSecond` (от начала запроса), `stageSeconds` — сумма `seconds`
каждого шага и число целей по готовым целям без ответов из кэша (для
среднего), `items` — по цели на каждый элемент запроса: `index`, `status`
(`queued` — ещё в очереди пакета, `running`, `done`), `stage` (первый идущий
шаг, только `running`), `seconds`, `cached` (ответ из кэша, такой же
проверки или такой же цели в этом пакете), `verdict` (статус ответа; `null`,
пока не готово, и у непроверенной цели остановленного пакета).

Где хранится. Ход живёт в памяти процесса API, как и ход выписки
обязанностей. Законченный ход хранится `PROGRESS_KEEP_SECONDS` (60 с) —
интерфейс берёт последний снимок после ответа, — а удаляется при заведении
следующего. Записей не больше `PROGRESS_MAX` (1000): сверх него проверка идёт
без хода, интерфейс получает `404` и блок хода не показывает. Удачные опросы
в журнал аудита не пишутся.

Ограничение: процесс API один — uvicorn без `--workers` (`api/Dockerfile`),
контейнер `api` без реплик. Если запустить несколько процессов или реплик,
опрос попадёт в процесс, где хода нет, получит `404`, и интерфейс перестанет
опрашивать (проверка при этом не страдает). Тогда ход нужно вынести в общее
хранилище или закрепить опрос за процессом (sticky по `X-Check-Id`).
